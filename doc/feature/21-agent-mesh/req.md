## 1. 目标

让**同一个 hub 账号下的多台主机**上的 DSH agent 能够互相发现、互相派活、互相问答：

- 用户在**任意一台**自己的 DSH 里工作，可以让当前 agent 去联络**另一台**主机上的 agent（"嘿 A，让 B 去做 X"），结果回到当前会话；
- 全过程**不新增端口、不需要公网 IP**（复用既有出站隧道）；
- 消息内容**端到端加密**，hub 只能看到"谁发给谁、什么时候、多大"这类路由元数据；
- 人类全程**可见、可控、可叫停**；且**不破坏**现有远程访问能力。

## 2. 范围

**在范围内**：同账号多机 agent 的发现 / 寻址 / 单向投递 / 请求-应答 / **广播与散射-收集** / 长任务进度 / 取消 / 隔离与授权 / 端到端加密与签名 / 作为 DSH 插件安装。

**不在范围内**（明确不做）：

| 非目标 | 说明 |
|---|---|
| 跨账号（不同 owner）通信 | D20：一律拒绝；配对/审批机制不做 |
| 多跳转发（A→B→C） | 仅单跳（D18） |
| **总线 / 订阅（topic + retention）** | 本期不实现；**另立特性 `22-agent-bus`**——涉及群组密钥、保留与位点语义、主题 ACL/配额（见 discussion §10 / D24） |
| 跨主机共享会话或上下文 | 会话保持主机本地，只传消息（D12） |
| 离线队列 / 消息持久重投 | P1 立即失败（D22）；队列留 P4 |
| 自动能力路由（"谁会做 X"自动挑机） | P4 |
| agent 获得对端 UI/终端访问权 | 永不（D13） |
| 移动端 / portal 的 mesh 拓扑界面 | 本期不需要（P2/P4 再议） |

## 3. 需求列表（含可判定验收标准）

| # | 需求 | 验收标准 | 阶段 |
|---|---|---|---|
| **R1** | **发现**：可列出同一账号内已开启 mesh 的其他主机（名称、在线状态、能力标签） | ① B 开启 mesh 后 ≤30s 内出现在 A 的 peer 列表（含名称与在线态）；② B 关闭 mesh 后从列表消失；③ **不同账号的主机永不出现** | P0 |
| **R2** | **寻址**：用人类可读的主机名指定对端 | 用主机名可成功投递；名称不存在时返回可读错误（不回退到 UUID 或静默失败） | P0/P1 |
| **R3** | **单向投递**：把一段内容投给对端 agent，并得到"已接收"确认 | ① 返回投递确认（含对端接收时间）；② 对端收件会话出现该内容；③ 对端未开 mesh / 方向不允许时拒绝并说明原因 | P1 |
| **R4** | **请求-应答**：投递并取回对端的最终答复 | ① 快任务（≤60s）直接返回答复；② 超 60s 返回任务标识，可等待/轮询取回；③ 默认总上限 10 分钟，超时有明确错误；④ "N 分钟无进度"提前失败 | P2 |
| **R5** | **长任务进度可见**：等待期间能看出"仍在跑 / 卡住" | 进度至少每 15s 或状态变化时更新（busy/idle + 最近活动时间）；**不含**对端内部推理或逐 token 输出 | P2 |
| **R6** | **可取消**：发起方可随时叫停进行中的跨主机任务 | A 取消后 ≤10s 内 B 侧会话被取消，两端状态一致（均显示已取消） | P1/P2 |
| **R7** | **离线语义**：对端不可达时快速失败 | 对端离线 / 未开 mesh 时**立即**返回可读错误；**不排队、不静默丢弃** | P1 |
| **R8** | **隔离**：只有同一账号、且已开启 mesh 的主机可互通 | ① 跨账号投递一律被拒（无论对方是否开 mesh，且错误可读）；② 被分享（member）给其他账号的主机，其 agent **不参与**本账号 mesh | P0/P1 |
| **R9** | **机密性**：载荷端到端加密，hub 只看到路由元数据 | ① 在 hub 侧采集数据**无法还原 payload 明文**；② 被篡改的消息被对端拒绝；③ 两端可核对对端身份（可选加固） | P1（与首个带载荷版本同期） |
| **R10** | **真实性**：消息与能力卡不可冒名 | 伪造/篡改签名的能力卡与消息被拒绝 | P1 |
| **R11** | **不破坏现有能力**：交付不得影响现有远程访问 | ① 线协议字节级不变（无新帧类型）；② 不修改 gateway 转发逻辑与 `dsh-web-remote`；③ **不安装**该插件时，现有功能零变化 | P0/P1 |
| **R12** | **可安装、可自检**：作为 DSH 插件安装；环境不满足时明确报错 | ① 可通过 `dsh plugin add` 安装；② 未接入 hub / 未开 mesh 时，工具返回可读错误而非静默失败 | P0 |
| **R13** | **运行实例边界明确**：行为与文档一致 | 文档写明消息落在"隧道持有者那个 dsh 实例"；实测结论与文档一致 | P1 |
| **R14** | **广播 / 散射-收集**：一次调用投递给全部（或指定子集的）已开启 mesh 的 peer；可等待并聚合回复 | ① 一次调用把同一内容投给 N 台，每台收到的内容与 1 对 1 投递**完全一致**（同一信封、同样的端到端加密与同样的隔离规则）；② 返回**逐台**结果（成功 / 失败原因），**单台失败不导致整体失败**；③ 散射-收集：可等待全部回复并聚合，受 D21 的超时/取消约束；④ **不形成回复风暴**：广播默认不要求回复，回复亦不回发广播（如需收集必须显式声明）+ 去重/防环（D18）；⑤ 离线机台按 D22 立即失败，其余不受影响；⑥ 有目标数上限与速率上限（默认值待定，需可配） | **P1.5（扇出投递）→ P2.5（聚合）** |
| **R15** | **威胁模型诚实 + 对端密钥固定**：文档与实现都不夸大 E2EE 的边界，并用本地 pin 防密钥替换（对应 D10 细化） | ① 文档明确写出：**防被动窃听 / 防第三方 ✓；防恶意 hub 的主动 MITM ✗（除非人工比对过指纹）**；② 对端公钥首次出现即**本地 pin**（TOFU，键 = hostId + 指纹），之后**变更 ⇒ 拒绝该消息 + 可读告警 + 需人工显式重新 pin**；③ 验收：模拟 hub 替换对端公钥 ⇒ 消息被拒且告警可见 | P1 |
| **R16** | **prompt injection 边界**：入站 mesh 内容以"**请求**"而非"**本人指令**"的形态进入收件会话（对应 D13/D15/D25） | ① 可信头由插件用**验签后的字段**生成（`@账号/主机名 (短 hostId)`，首次或指纹变更时含指纹），正文与头有明确分隔；② payload 内自封身份（"我是 X"）**不影响**头部；③ 收件侧 agent 对本机**破坏性操作**仍走 DSH 既有的人类确认 —— mesh 免审批不构成该例外；④ 验收：构造一条自称是另一台 host 的消息 ⇒ 头部显示真实发送方；⑤ **首次接触可见**：对某 peer 的第一条消息在可信头标注"**新 peer**"，`mesh peers` 列表同样标注到用户看过为止 —— **不阻塞投递**（R17 不采纳，见 §7 与 `discussion.md` §9.9） | P1 |

## 4. 约束与不变量

1. **仅同账号**（D20）；跨账号一律拒绝。
2. **单隧道铁律不变**：本特性**不建隧道**，依赖本机已通过 CLI 服务或 `dsh-web-remote` 接入 hub（D9）；不抢 `join.lock`。
3. **不重构现有组件**：host 侧为独立插件；hub 侧仅加法式新增；线协议与 gateway 转发零改动（D8）。
4. **会话保持主机本地**：跨主机只传消息，不共享上下文（D12）。
5. **访问层级**：mesh 只给 L0（消息）；L1（旁观单个会话）与 L2（进整台机器）**都不给 agent**，L2 必须走显式 `host_share`（D13）。
6. **入站落专用收件会话**，绝不默认插入人类正在使用的会话（D16）。
7. **仅单跳** + 跳数上限/去重（D18）。
8. **每主机可控**：mesh 默认关闭；开启后可限定方向（send-only / receive-only / both）与可接受的能力范围（D14/D19）。
9. **DSH 版本**：工具注册与会话注入 API 在 dsh `0.1.2-rc.1` 与 `0.1.5-rc.2` 均可用（审计已确认）。
10. **身份用稳定 ID（D25）**：`owner_id` + host UUID 承载身份与 pin；`name` 仅展示层，由接收侧按 hostId 解析（解析不到退回 hostId）。
11. **入站内容分"可信头 / 不可信正文"**：接收侧顺序固定为 **先验签 → 再解密 → 再 prompt**；hub 签名头须防重放（`timestamp + nonce + body hash`，拒绝 >60s 偏移）。
12. **威胁模型边界诚实（R15）**：不承诺防恶意 hub 的主动 MITM；密钥变更以"拒绝 + 告警 + 人工重新 pin"处理，不做撤销广播。
13. **开启即授权 + 可撤回 + 可审计（D15 边界）**：mesh 开关文案即授权声明（开启 = 允许同一账号内已开 mesh 的主机向本机派活，受方向/能力/限速约束）；撤回（关 mesh / 改方向 / 拉黑单台）**≤30s 生效**；每次跨主机投递留 from/to/时间/大小/结果审计。**不设逐 peer 人工闸门**（R17 不采纳）；账号内横向移动的残余风险按 R16 + D19 + 审计约束（`discussion.md` §6.3.6）。

## 5. 端到端验收剧本

环境：同一账号下两台真实主机（如 `iMacPro` 与 `office-mac-studio`），各跑一个 `dsh web` 并已接入 hub；均安装本插件（B 需开启 mesh）。

| 步 | 操作 | 通过条件 |
|---|---|---|
| 1 | A 上执行 peer 列表 | 看到 B（名称 + 在线 + 能力标签）；看不到非本账号主机 |
| 2 | A 上让 agent 请求 B 做一件**快任务** | 结果回到 A 的会话；B 的收件会话出现该请求与执行记录 |
| 3 | A 上让 agent 请求 B 做一件**超 60s 的任务** | A 侧转为可等待的任务并在期间看到节流进度；完成后取回结果 |
| 4 | 在第 3 步进行中，A 侧取消 | ≤10s 内 B 侧会话被取消；两端状态一致 |
| 5 | 关闭 B 的 mesh 或不启动 B，A 再投递 | **立即**失败并给出可读原因（"对端离线 / 未开 mesh"）；不排队 |
| 6 | 在 hub 侧采集网络/数据 | 只能看到路由元数据（from/to/时间/大小），**看不到 payload 明文** |
| 7 | 用另一账号的主机 C 尝试投递给 A | 一律被拒绝（无论 C 是否开 mesh） |
| 8 | A 广播一条消息给全部 peer（含一台离线的 D） | 在线各台均收到；离线那台**单独**失败并给出原因；A 拿到逐台结果；不产生回复风暴 |
| 9 | A 广播并收集（散射-收集） | 在线各台的回复被聚合返回；期间可见进度、可取消（D21） |
| 10 | 卸载本插件后回归 | 现有远程访问（portal 进入、`rdsh host serve`）行为完全不变 |

## 6. 依赖与前置

1. **心跳超时修复先完成**（D7）：`doc/fix/20260911-heartbeat-pong-timeout/` —— 因为"在线"是 peer 列表的核心字段。
2. **hub 需要发布/部署**带 agent 索引与投递 API 的新版本（加法式；老 hub 上应给出"不支持"的明确错误）。
3. 两台真实 host 已接入同一 hub 账号，且 DSH 版本 ≥ `0.1.2-rc.1`。
4. 本机已有隧道（CLI 服务或 `dsh-web-remote`），本插件不负责建立。

## 7. 决策结论（2026-09-11 已定）

原 §7 的 13 组待确认决策已逐条给结论（完整论证见 `discussion.md` §6 / §8）：

| 决策 | 结论（摘要） | 影响的需求 |
|---|---|---|
| D2 | E2EE **与 P1 同期上线**（P0 纯发现不传载荷、无需加密） | R9 的排期 |
| D3 | MVP 走"hub API + 既有转发 + 插件路由"，**零线协议改动**；可行性已核实（gateway 转发无路径白名单，`proxy.ts:81/143`） | R11、整体工期 |
| D4 | hub 侧 `owner_id` 相等 + host 侧验签/开关/方向/能力校验；**补**防重放（ts+nonce+body hash）与"身份以 hub 断言为准" | R8 |
| D5 | `@deepseek-ai/dsh-tools` 声明为 **peerDependency**（避免第二份模块实例）+ 兼容范围 + 缺失时明确报错 | R12、跨版本稳定性 |
| D6 | 承诺写精确为"**老 host/gateway 永不因 hub 升级失效；新增帧类型须向后兼容 + 能力协商**"；本期不动用该例外 | R11 |
| D8/D9 | 新插件 + hub 加法，**不建隧道**；插件须装在"隧道持有者那个 dsh profile"并提供自检；文档写明**一 token 一隧道** | R11、R12、R13 |
| D10/D11 | X25519 ECDH + Ed25519 签名 + **TOFU 本地 pin**；KDF 独立 label + AAD、随机 12B nonce；**先验签 → 再解密**；密钥变更 = 拒绝 + 告警 + 人工重新 pin（不做撤销广播） | R9、R10 |
| D12/D13 | 代表制 + 会话保持本地（**按安全不变量对待**）；**mesh 只给 L0，agent 永不获得 L1/L2** | 整体体验、R11 |
| D14 | 主机级开关（默认关）+ 能力标签默认最小 + 变更即时上报 + AgentCard **TTL 90s** | R1、R8、R12 |
| D15 | 同 owner 免逐次审批，以"可见 + 可叫停"替代（代价由 D19 上限 + 审计 + R16 约束） | R6、R8 |
| D17 | 共享成员不入 mesh（双向），peer 列表不出现"分享给我的 host" | R8 |
| D18 | 仅单跳 + `visited`/跳数上限/`correlationId` 去重；**`reply` 永不触发新的 ask** + 每对 peer 限速熔断 | R8、R11 |
| D19 | 每主机 send-only / receive-only / both + 能力白名单；**接收侧校验为准**；默认能力白名单最小、每对 peer 限速 | R8、R13 |
| **D25** | **身份与展示分离**：wire 用稳定 ID（`owner_id` / host UUID），`name` 仅展示层；pin 与授权键 = hostId + 指纹；人类可见头由**验签字段**生成 | R3、R10、R16 |

**本轮新增需求（已并入 §3）**：**R15**（威胁模型诚实化 + 对端密钥 pin）、**R16**（prompt injection 边界）。

**R17（首次接触确认）已定：不采纳**（2026-09-11）——“**开启 mesh 本身就是一次授权动作**”：一个 peer 能出现的前提是 owner 自己签发 join token、在那台机器 `rdsh host join`、并安装启用本插件；同账号 = 已授权，逐 peer 再确认属重复授权。且该闸门只对"每对 peer 的第一条"生效（点过一次即永久开放），对 injection 的实际防护 ≈ 一次性减速带，却要新增 pending 语义、headless 审批路径与离线队列的审批定义。替代为**不阻塞**的方案：**开启文案即授权声明 + 首次接触可见（R16 ⑤）+ 可撤回 + 审计**（§4.13）；残余风险见 `discussion.md` §6.3.6。

> 前几轮已定：D1（命名）、D7（心跳修复，已实施）、D16（身份粒度）、D20（仅同 owner）、D21（长任务进度/取消）、D22（离线语义）、D23（运行实例边界）、**D24（广播纳入本期 P1.5/P2.5；总线/订阅另立 `22-agent-bus`）**。
