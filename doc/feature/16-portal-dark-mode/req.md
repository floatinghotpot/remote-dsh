# portal 深色模式（req）

> **日期**: 2026-09-11
> **上游**: [discussion.md](discussion.md)（事实审计）
> **状态**: **待批准**（本文件获批后方可编写 `solution.md`）
> **范围**: `packages/portal` 前端源码

---

## 1. 目标

`rdsh-portal` 在**操作系统 / 浏览器处于深色模式**时，整体呈现协调的深色外观，不出现白底残留与对比度失效；浅色模式下的现有外观不发生非预期回归。不新增手动切换入口。

## 2. 需求

### R1 跟随系统深色偏好

portal 依据 `prefers-color-scheme: dark` 自动切换外观，**不提供**手动切换开关（已决策）。

- **验收**：在系统深色模式下打开任一 portal 路由，页面为深色；切回浅色模式后无需刷新（或仅需刷新一次即可）恢复浅色。
- **验收**：portal 内不存在主题切换入口。

### R2 全部页面的深色覆盖

深色下 `App` 路由分发（`packages/portal/src/pages.tsx:62-97`）覆盖的**全部**页面均无固定浅色残留，包括无壳页（登录/注册/法务/产品/验证/重置密码）、应用壳页（主机列表/添加主机/订阅/账户与安全各设置页）与管理后台（`/admin` 及其子路由）。

- **验收**：逐页人工核验，深色下不存在「白色卡片」「白底代码块」「白底下拉菜单」「白底模态框」等割裂色块。

### R3 语义化配色层

页面组件的配色改为**语义化引用**（同一语义在浅/深两套取值下切换），不再由散落的字面色值决定。

- **验收**：新增或修改的颜色不再以字面 hex 直接出现在 JSX 内联样式中；页面底色、卡片、描边、正文/次级/弱化文本、主色、危险色、成功色、选中态、遮罩等语义均有明确取值。

### R4 原生控件与浏览器 UI 适配

深色下原生表单控件（`<input>` 17 / `<select>` 4 / `<textarea>` 2）以及滚动条、默认控件弹层（如日期选择）呈现深色外观，且文字、占位符可读。

- **验收**：深色下依次核验登录、注册、验证、账户设置、管理后台表单，控件底色与文字不出现白底浅字或白底刺眼；占位符可辨识。

### R5 二维码可扫描性

深色下 TOTP 绑定二维码（`pages.tsx:1053`）与微信支付二维码（`pages.tsx:1857`）仍可被正常扫描。

- **验收**：深色下两个二维码均能被对应客户端成功识别。

### R6 对比度达标

深色与浅色两套外观下的正文文本对比度满足 WCAG 2.1 AA：正文 ≥ 4.5:1，大字号（≥18.66px 粗体或 ≥24px）≥ 3:1。危险色、成功色、主色在各自底色上保持可辨识。

- **验收**：对主要文本/背景组合取样计算对比度，全部达标；给出取样清单与计算依据。

### R7 阴影与遮罩适配

深色下模态遮罩、下拉菜单与弹窗投影仍能形成可见的层次区分（不得因黑色投影而失去分层）。

- **验收**：打开模态框、下拉菜单、管理后台弹窗，深色下层次清晰、遮罩可见。

### R8 媒体资产的深色表现

`/product` 页引用的白底架构图（`public/media/rdsh-arch.jpg`）在深色下不呈现为刺眼白块。

- **验收**：深色下 `/product` 页该图的呈现方式经确认可接受（处理方式见 §4 待确认项 Q3）。

### R9 声明 `color-scheme`

页面向浏览器声明其支持的配色方案，使 UA 渲染的控件、滚动条、表单弹层与页面配色一致。

- **验收**：深色下原生滚动条与控件跟随深色；不出现「深色页面 + 浅色滚动条」的割裂。

### R10 浅色外观不回归

浅色模式下 portal 外观与现状保持一致；仅允许因语义色合并产生的不可感知或极小差异，且须逐项说明。

- **验收**：浅色下逐页与改动前对比，列出全部可感知差异并逐项说明理由。

### R11 构建与测试零缺陷

- **验收**：`pnpm build`（tsc strict）零 issue；`pnpm test` 全绿；portal 包 `vite build` 成功产出。

### R12 深色下微信按钮反转前景/背景（2026-09-11 追加）

深色模式下，微信登录按钮改为**深色底 + 品牌绿前景**（图标、文字、描边均为 `#07c160`），替代「绿底 + 白字」；浅色模式维持「绿底 + 白字」不变。

- **背景**：现状「绿底 + 白字」对比度为 **2.38:1**，不达 AA（R6 深色列唯一 FAIL）。反转后「绿前景 + 深底」在页面底 `#151517` 上为 **7.65:1**、卡片 `#232324` 上为 **6.58:1**，均达标。
- **品牌一致性**：品牌绿仍出现在图标、文字与描边三处，识别度不降。
- **验收**：深色下微信登录按钮为深底绿字绿图标且对比度达标；浅色下与改动前逐字一致。

## 3. 非目标

- **N1** 不做手动主题切换（不含三态开关、不含用户偏好持久化）。
- **N2** 不修改 `packages/hub`、`packages/gateway`、`packages/tunnel`、`packages/web-remote`、`apps/*`、`go/`。
- **N3** 不改动部署形态与服务单元（不重启、不修改 `rdsh-hub.service` / `rdsh-join.service` 及其配置）；本次仅在 hub 主机上以工作区构建做真机验证，见 §5。
- **N4** 不引入 CSS 框架或 UI 组件库；不新增运行时依赖（`qrcode` / `react` / `react-dom` 之外）。
- **N5** 不做超出深色适配范围的视觉重设计（间距、字号、布局、文案均不变）。
- **N6** 不新增浏览器自动化/视觉回归测试基建（当前 portal 无该能力）。

## 4. 待确认项（需拍板后方可进入 solution）

- **Q1 深色配色基线**：自定义深色取值，还是贴近 DSH 官方深色观感（`--dsw-alias-*` 体系的深色值）？
- **Q2 品牌色处理**：主色 `#2563eb` 与微信绿 `#07c160` 在深色下保留原值，还是各自提亮以保证对比度？
- **Q3 架构图处理**：为 `rdsh-arch.jpg` 提供深色变体（需出图），还是在容器层适配（加浅色卡片容器 / 允许点击放大）？
- **Q4 浅色差异容忍度**：R10 是否允许把 `#666`/`#999`/`#6b7280`/`#9ca3af` 等近似色归并为更少的语义色（会带来肉眼几乎不可见的浅色差异）？
- **Q5 验收取证方式**：深色验收以人工逐页核验 + 对比度计算为准（无自动化视觉回归），是否认可？

## 5. 交付与验证流程（已决策）

本次采用「在 hub 主机上就地开发 → 真机验证 → 提交推送 → 异地发布」的流程：

1. **就地开发**：直接在 hub 主机（本机 `aliyun-ubuntu26-rdsh-host`）的 `packages/portal` 源码上改动。
2. **就地构建并真机验证**：`packages/hub` 的构建脚本 `scripts/copy-portal.mjs` 会把 `packages/portal/dist` 复制到 `packages/hub/portal`（`packages/hub/scripts/copy-portal.mjs:11-13`）；线上 hub 进程对 portal 是**每请求读盘**（`packages/hub/src/portal.ts:36-79`），因此构建完成后**刷新 `https://rdsh.cn/portal` 即可看到改动，无需重启服务**。
3. **验证期间不得重启 hub**：当前 hub 进程解析到的是工作区构建；一旦重启会切回全局 npm 包内的已发布产物（见 [discussion.md](discussion.md) §6），验证会中断。
4. **提交推送**：验证通过后，按仓库 §6 显式路径提交流程 commit & push 到 GitHub。
5. **异地发布**：由另一台 dev 主机执行 hub 包发布（本机不发布）。

- **验收**：上述第 2 步的构建命令零报错，`https://rdsh.cn/portal` 真机呈现深色外观。
