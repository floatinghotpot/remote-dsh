## 1. 背景与目标

proposal Q1 定案"自用/自托管起步、架构预留多租户扩展、价值验证后再商业化"——现在走到"价值验证"节点：hub 已支持多用户 + join token 自助接入（05），账号安全体系在 M5 加固，**商业化（付费托管 hub）的条件开始具备**。

**目标**：让用户**自助注册 → 邮箱验证 → 试用 → 付费订阅**一台托管 hub，按账号管理多台机器；运营方（你）获得收入与运营数据。

**形态并存**：自托管形态不变（开源免费）；SaaS 是"我们替你托管 hub"的服务，不是闭源化。

## 3. 需求拆解

### 3.1 用户提出的三项

**① 邮箱自助注册 + PIN 验证**
- `POST /api/auth/register {email, password}` → 发 PIN（6 位，TTL 如 10 分钟，重发限流）→ `POST /api/auth/verify {email, pin}` → 账号激活
- 注册关闭策略反转：SaaS 形态**开放注册**（自托管形态仍可关闭——配置项）
- 与 M5 邮箱绑定决策衔接（用户名 = 邮箱？还是 name + email 双字段？—— 见 D1）

**② 认证控制 + 到期 + 计费 + 支付（微信/支付宝）**
- 账号状态机：`registered → verified → trial → subscribed | expired | banned`
- 订阅：`POST /api/billing/subscribe {planId}` → 生成支付订单 → 跳转微信/支付宝收银台 → **支付回调（异步通知）→ 幂等入账 → 激活订阅**
- 到期：订阅到期 → 降级/停用规则（见 3.2-④）
- 微信/支付宝：服务端签名（RSA）+ 回调验签 + 对账（订单状态核对）

**③ 试用逻辑**
- 邮箱验证后自动进入试用：**1 台 host 配额**，时长待定（见 D2：几小时 / 3 天 / 7 天）
- 试用到期 → 提示订阅或停用（降级规则一致）

### 3.2 补充思考（"what else" —— 商业化必须想清楚的）

**① 套餐与定价模型（D3）**
- 维度：按 **host 数量 × 订阅时长**（简单起步）vs 按用量（带宽/存储，后置）
- 档位建议：Free（0 台，仅体验 portal？）/ Trial（1 台，限时）/ Pro（N 台）/ Team（更多 + 共享）
- 定价数字是商业决策，本管线只定**模型与配额语义**，价格可配置（config 或运营表）

**② 订阅生命周期与状态机（D4）**
- 状态机必须覆盖：trial → expired → subscribed → renew → cancel（到期不续）→ downgrade → refund → banned
- **支付回调幂等**（同一订单重复通知只入账一次）；对账（日终对账任务）

**③ 订单/订阅数据模型（技术面）**
- `users` 加 `email/email_verified/plan/trial_start/trial_end`；新表 `orders`（支付单）、`subscriptions`（订阅期）、`payments`（入账流水，含渠道单号）
- 配额检查落地：**register 端点消费 05 预留钩子** —— 按账号 plan 检查 host 数上限（试用=1）

**④ 过期/降级处理（D5）—— 商业化体验的关键**
- 订阅/试用到期后：① 立即停全部隧道？② grace 期（如 3 天只读/可续）？③ 降级到免费档 host 数（保留最早 N 台，其余离线）？
- **数据保留**：离线 host 数据保留多久？删除账号时彻底清除（合规）
- 建议：到期 → 3 天 grace（portal 提示续费，隧道保留）→ 降级到免费档（超出 host 离线但数据保留 X 天）→ 删除

**⑤ 合规与资质前置（D6）—— 必须诚实面对的门槛**
- **支付资质**：微信支付商户号 / 支付宝开放平台商户均需**企业资质**（个体工商户可申请微信支付；支付宝企业认证）。个人开发者无法直接接入 → 需注册个体户/公司（或先接"易支付/第四方"灰色通道——**不推荐**，违规风险）
- **经营性许可**：提供付费互联网服务 = 经营性 ICP → 需 **ICP 经营许可证（EDI）**（非经营性备案不够）；涉及支付还需持牌机构通道（即商户号）
- **发票**：用户可能要求发票（数电票）→ 开票能力（自开或第三方）
- **隐私/个保法**：隐私政策、用户协议、数据删除入口、日志脱敏
- 这些是**上线前置**而非本管线实现项，但影响排期与投入决策，必须在讨论阶段明确

**⑥ 反滥用（SaaS 必答题）**
- 注册 bot：邮箱 PIN + 图形/行为验证码（或邮箱验证码限流）
- 薅试用：同 IP/设备/邮箱域名多账号 → 风控规则（试用期短 + 邮箱验证已挡掉大部分）
- 滥用 host：注册即开隧道 → 被用于爬虫/垃圾 → 滥用检测与封禁（banned 状态机）
- 支付欺诈：拒付/退款率监控

**⑦ 安全强化（依赖 M5）**
- 公共 SaaS 必须把 M5 全部落地：登录风控（账户锁定）、2FA、审计日志（付费操作审计）、join token 安全
- **E2E 加密（Q5）**：公共 SaaS 的 hub 可见用户明文会话 —— 必须实现层 2 加密位（协议已预留），否则用户数据过托管 hub = 信任运营方；这是 SaaS 化的技术分水岭，建议与 08 并行立项（或作为 08 的 P0 子项）
- 订阅/支付相关端点限流 + 审计（谁支付、谁改套餐）

**⑧ 运营配套（轻量起步）**
- 优惠码/促销（后续）；退款策略（如 7 天无理由，中国消保法对线上服务有要求）；客服渠道（邮箱/工单）
- 用量看板（运营方）：注册数、订阅数、MRR、host 数 —— 复用 07 审计 + 新增运营查询

**⑨ 技术底座（评估项）**
- SQLite 单文件 → SaaS 多用户/并发：**评估 PostgreSQL 迁移**（或先 SQLite + 备份策略，量级到了再迁）
- 支付回调必须公网可达（已有 443 反代）；回调签名验签（微信/支付宝 RSA）
- 可用性：备份（DB 每日）、监控告警、升级演练（M6 一部分）

## 4. 关键设计问题（进 req.md 前需定）

| # | 问题 | 倾向 | 需确认 |
|---|---|---|---|
| D1 | 用户名模型 | **email 即用户名**（SaaS）vs name+email 双字段（兼容自托管） | 两形态是否共用同一代码路径（配置切换注册开关） |
| D2 | 试用时长 | **3 天 1 host**（用户提议 3 天或几小时之间取平衡；几小时转化差，7 天防滥用弱） | 3 天 vs 7 天 |
| D3 | 定价模型 | host 数 × 时长；价格可配置 | 档位数量与配额（Free/Trial/Pro/Team 的 host 数） |
| D4 | 订阅状态机边界 | trial → grace(3d) → 降级免费档 → 数据保留 X 天 → 删除 | grace 天数、免费档 host 数、保留期 |
| D5 | 支付接入范围 | **微信 + 支付宝商户号**（需企业资质） | 是否接受"先人工收款/邀请制过渡"（资质办下来前） |
| D6 | E2E 加密 | **08 的 P0 子项**（Q5 承诺 + 数据合规） | 与 08 并行还是先做 |
| D7 | 注册开放范围 | SaaS 形态开放注册；自托管形态保留"注册关闭"配置 | 同一代码路径开关 |
| D8 | 反滥用强度 | PIN + 限流 + 试用期短 | 是否上图形验证码（MVP 可后置） |
| D9 | 数据库 | 评估 PG 迁移时机 | MVP 先用 SQLite + 每日备份？ |
| D10 | 退款/发票 | 数电票（对接第三方开票）+ 7 天退款 | MVP 是否只做退款不做开票 |

## 5. 合规与资质前置（独立成节，诚实记录）

| 项 | 现状 | 影响 |
|---|---|---|
| 支付资质（微信/支付宝商户号） | **需企业资质**（个体户/公司） | **阻塞付费功能上线**；建议先注册主体（可并行 M6） |
| 经营性 ICP 许可（EDI） | 付费服务需要（非经营性备案不够） | 中长周期（审批），尽早启动 |
| 域名 ICP 备案 | M6 事项（hub 域名已用 LE 证书，备案未做） | 上线前置 |
| 隐私政策/用户协议/数据删除 | proposal §6.6 已列，未实现 | 上线前置 |
| 发票 | 数电票需对接 | 可后置（MVP 退款不开发票，提前声明） |

> 结论：**商业化的真正瓶颈不在技术，在资质**。建议：技术管线（08）与资质办理（M6 扩展）**并行启动**；资质未落地前可先"邀请制/人工开通"验证需求（D5）。

## 6. 技术约束备忘

- **依赖最小化**：支付 SDK 是合理例外（微信/支付宝官方 SDK 或手写 RSA 签名+回调验签，量可控）；TOTP/邮件复用 07 决策
- **协议先行**：新增层 1 API（register/verify/billing/subscribe/callback）契约文档先行（协议纪律）
- **幂等**：支付回调、订阅激活、配额检查全部幂等；对账任务兜底
- **配额钩子消费**：register 端点（05 预留）接账号 plan 检查 —— 这是 08 与 05 的交汇点
- **E2E 加密**：层 2 帧 flags bit0 加密位实现（Q5）—— 建议单独立项但 08 排期考虑
