## 1. 目标

让**与 host 处于同一内网**的客户端，**直接访问该 host 的 DSH**，不再为访问同一台机器而绕公网 hub 一圈：

- **省流量 / 降延迟**：工作区文件、事件流、页面 RPC 走内网；
- **降 hub 压力**：hub 的出口带宽与并发压力显著下降（运维方成本直接受益）；
- **不牺牲体验与安全**：引导/握手仍可经 hub（体量小、一次性）；直连不可用时**自动回落隧道**，体验不劣于现状；门禁（主机固定口令）在两条通道上一致生效；
- **同一台机器、同一个智能体**：直连与隧道是同一 dsh 实例的两个入口，不是两个 DSH。

**内网地址不经过 hub**：客户端在**既有的端到端加密通道**内向 host 索取内网候选（host 不向 hub 上报，hub 不存储、不可见、也无从伪造）。

| 非目标 | 说明 |
|---|---|
| **hub 的任何改动** | 不加 API、不改表、不改层 2 协议与 relay/shim（D17 选 c；候选下发走既有 E2EE 通道） |

### 术语约定（速查，避免歧义）

| 术语 | 定义 |
|---|---|
| **host / 客户端** | host = 跑 DSH 并被远程访问的机器（两种形态：CLI 起的、插件注册的）；客户端 = 本期仅 App（garsync WebView） |
| **隧道** | host 出站到 hub 的既有加密通道（join）；本特性**不改动**它 |
| **直连 / 直连口** | 客户端直接访问 host 的内网监听端口；直连口 = host 在 join 之外额外监听的内网端口，转发到同一个 dsh |
| **候选** | host 的内网地址（IP + 端口）列表，经 E2EE 通道下发给客户端；**不经过 hub** |
| **固定口令 / 门禁** | host 所有者设定的单一口令（`gateway.accessCode` 语义）；两条通道共用；门禁 = 用它挡未授权访问 |
| **E2EE 通道** | 浏览器↔host 的端到端加密数据面（09 号）；本特性复用它在 hub 不可见的前提下传候选与直连票 |
| **直连票 / direct ticket**（R4） | host 随候选经 E2EE 下发的**一次性凭据**，客户端拼到直连 URL，直连口校验后 303 换会话 cookie ⇒ 免重输口令；**签名密钥 = per-host 随机密钥 `~/.rdsh/direct-secret`（独立于口令）**；代码标识符建议 `directTicket` |
| **页面授权 token**（R7） | host 注入到**已过 gate 的页面**、客户端经 E2EE 内层请求回传的一次性凭据，用于授权 raw 流 ⇒ 修 raw 流绕过 |

> ⚠️ **两个凭据不可混用**：**直连票**（R4，用于直连首访，走 E2EE 下发）与 **页面授权 token**（R7，用于授权 raw 流，走页面注入 + 内层回传）用途、通道、消费方都不同。


## 3. 需求列表（含可判定验收标准）

|---|---|---|---|
| **R1** | **双通道并存（同一 dsh 实例）**：join 模式下 host 同时保持 hub 隧道与内网直连口，两者指向**同一个** dsh | ① 隧道在线时，内网端口可访问并返回 DSH 页面；② 关掉直连口不影响隧道，反之亦然；③ 两个入口看到**同一个**工作区/会话列表；④ 进程核对：只有**一个** `dsh web` 子进程；⑤ 直连监听地址与端口**可由配置指定**，且候选必须包含**实际监听端口** | P1 |
| **R2** | **两种 host 形态都具备直连口** | ① CLI 形态（`rdsh host serve`）与② 插件形态（`dsh-web-remote`）分别都能在内网端口访问到 DSH，且各自仍保持隧道在线 | P1 |
| **R3** | **候选下发不经 hub**：host 在 E2EE 通道内提供本机内网候选 | ① 客户端经 E2EE 通道取得候选；② 候选**至少含全部非 loopback 接口的 IPv4 + 实际监听端口**（IPv6 / mDNS 名列为**可选**，P3+ 再评估）；③ hub 侧不可见、不可伪造（日志/抓包只见 raw 流字节；DB 与 API 无任何新增）；④ 共享成员**不**获得候选；⑤ 候选**不在客户端持久化**（每次启动经隧道重取；IP 变化靠回落兜底，不靠缓存） | P1 |
| **R4** | **一次性直连凭据（直连票 / direct ticket）**：客户端把 E2EE 通道内取得的直连票用在直连 URL 上，免重复输入口令 | ① 直连票随候选经 E2EE 下发，**单次使用 + 短 TTL（建议 ≤30s）+ 绑定当次客户端会话**；② 直连首访用直连票换会话 cookie，地址栏**不残留**（303 重定向）；③ 直连票伪造 / 篡改 / 重放被拒；④ **签名密钥 = per-host 随机密钥（`~/.rdsh/direct-secret`，自动生成，方案 B）**，独立于口令——不设口令也能签发/校验直连票 | P1 |
| **R5** | **选路与自动回落**：优先直连；不可达/超时自动回落隧道 | ① 试连成功 → 走直连；② 失败 / 超时（阈值建议 ≤3s）→ 自动回落隧道，**无错误弹窗、会话不丢**；③ **网络变化时重新探测**（WiFi↔蜂窝、切换 WiFi）；④ 直连选择**按客户端独立**（多设备互不影响，各选各的）；⑤ 候选不持久化（见 R3⑤） | P2 |
| **R6** | **门禁模型（方案 B）**：直连口门禁 = ticket（始终）；口令（accessCode）为**可选增强层**；动态配对码废弃 | ① **未设口令**：直连口 = 纯 ticket 门禁（无票 403），隧道无门禁（= 现状）；② **已设口令**：直连口 = ticket + 口令（手动访问需口令），隧道也要求口令（feature 15）；③ 改口令后旧凭据（cookie）全部失效；④ `auth.mode: "pair"` 不可再被选中 | P1 |

## 4. 端到端验收场景

1. **同内网直连成功（主场景）**：手机与 host 同一 WiFi → App 经 hub 打开 host → App 取得候选 → 试连内网成功 → 切换后工作区/会话与切换前一致；此后的大流量（文件读写/事件流）不再经 hub。
2. **跨网段自动回落**：手机切到 4G/其他网络 → 试连候选失败 → 阈值内回落隧道，用户无感（无弹窗、会话不丢）。
3. **门禁两条通道一致**：host 设固定口令 → 隧道首访要求口令；直连首访用一次性 token 免重复输入；清除口令后两条通道都不再要求。
4. **门禁不可绕过**：用脚本（不经页面）直接向 host 开 E2EE raw 流 → 无任何响应且被关闭；同时正常 App 访问不受影响。
5. **两种 host 形态**：分别在 CLI 起的 host 与插件注册的 host 上重复场景 1。
6. **冒充防护**（R8）：在同一内网另起一台机器抢占该 IP:端口 → App 拒绝或告警，不静默连上。
7. **hub 零改动核对**：全过程 hub 无新增 API/表/协议字段；hub 侧看不到内网候选内容。

### P3 证书设计要点（插件形态必须一并考虑，用户 2026-09-27 提出）

| # | 要点 | 理由 / 事实 |
|---|---|---|
| 1 | **证书存共享位置（`~/.rdsh/`），两种形态同一份** | plugin 与 CLI 本就共用 `~/.rdsh`（host.json、token、E2EE 静态密钥）；证书同放 ⇒ **切形态不触发 App 重新信任**（否则指纹一变就要重新确认，体验与信任都会被削弱） |
| 2 | **优先复用 `host.json.tls`（用户已有证书时）** | 字段已存在（`TlsConfig {cert,key}`），cloud 模式用户本就有证书 ⇒ **这类用户零新增依赖** |
| 3 | **生成方式 = 纯 JS 库（`selfsigned`），不用 openssl**（已定，2026-09-27） | 插件是**进程内函数插件**，不能依赖外部命令（openssl 子进程观感差、Windows 无 openssl）；纯 JS 库两形态统一、无子进程、跨平台。需破一次"依赖最小化"纪律，理由见 C8 |
| 4 | **证书身份 = 这台 host，不绑定 IP** | App 靠**指纹**认身份、不核对证书里的名字/IP ⇒ **动态 IP 只换地址、不换身份，不会触发重新信任**。证书 SAN 里即便写了 IP 也只是辅助，App 并不依赖它 |
| 5 | **不自动轮换**；轮换必须显式且提示 | 证书即身份：静默轮换 = App 端信任全部失效 |
| 6 | 同机只有一个直连口持有证书 | CLI join 与插件互斥（join pid 锁，plugin 检测到 CLI 在跑会拒绝）⇒ 无并发冲突 |

## 7. 兼容性风险（哪些会不兼容，solution 阶段需逐条做调用点审计）

> 结论：**有 3 处破坏性 + 1 处隐蔽风险 + 1 处隐私依赖**；其余天然兼容。破坏性项必须配迁移 + 发布说明 + 大版本号。

### 7.1 会破坏兼容的（必须处理）

| # | 变更 | 谁被伤 | 必须做的兜底 |
|---|---|---|---|
| B1 | 移除 `auth.mode: "pair"` 与 `--pair-code` | **存量 lan 用户**：升级后 `normalizeConfig` 抛错（只认 `pair/password/none`，`config.ts:196`）→ 机器进不去 | `normalizeConfig` 里做迁移（旧 pair 配置 → 新默认 + 生成固定口令）；发布说明 + **大版本号** |
| B2 | `rdsh-gateway` 公共 API 变化：`AuthMode` 去掉 "pair"、`PairManager` 移除、`setup lan` 参数变 | **CLI**（`packages/cli`）与**插件**（`packages/web-remote`）都 import 了这些类型 | 同仓一起改；对外是 breaking，按 semver 升大版本 |
| B3 | M1 的 e2e 用例、博客、usage、README 全按配对码写 | 测试与文档 | R12 同步重写 |

### 7.2 隐蔽风险（最该提前盯）

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| B4 | **R7 的 raw 门禁是 fail-closed** | 设了口令的 host 要求"raw 流必须先凭页面里的授权 token 才服务"。一旦 host 注入的脚本因 DSH 升级 / CSP 收紧而**没跑起来**，连输对口令的正常用户也会被拒——表现为"突然连不上、看不出原因" | ① 门禁**仅在设了口令时启用**（无口令 host 完全不变）；② 留 **kill-switch**（临时关掉 raw 门禁）；③ 每个 DSH 新版本做一次注入脚本回归测试 |

### 7.3 隐私依赖

| # | 依赖 | 说明 | 处理 |
|---|---|---|---|
| B5 | 依赖 **hub 的 E2EE 开启 + 客户端已 pin**（C4） | 若某台 hub 配 `e2ee.mode=off` 或客户端没 pin，候选会变成明文走隧道 ⇒ "hub 不可见"失效 | 按 C4 降级：E2EE 未激活时**禁用直连优先**，一律走隧道 |

### 7.4 天然兼容（不必担心，仅备查）

- **层 2 隧道协议不动** → 未来 Go 重写的 hub、老 gateway、TS↔Go conformance 都不受影响。
- **hub 侧零改动** → 新 host 的候选端点只是 relay 的普通路径（relay 无路径白名单），老 hub / 新 hub 都直接转发。
- **客户端双向兼容**：老 App + 新 host → 老 App 不取候选，继续走隧道；新 App + 老 host → 取不到候选，自动回落隧道。都不崩。
- **独立 cloud 模式（`auth.mode: "password"`）不在废弃范围** → 现有 cloud 用户无感。⚠️ 但 D18「password 是否并入单一口令」未定，**一旦并入则又是一处 breaking**。
