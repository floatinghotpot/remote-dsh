## 1. 背景与目标

**触发**：09 拆两阶段讨论中，Token 转售被确认是**独立能力**——用户没有 DeepSeek key 也能用 DSH，购买我们的模型额度即可；它服务的不只是云端 host 用户，还有 08 的自有 host 用户 → 独立立项（10）。

**目标**：用户**无 key 也能跑 DSH**：portal 购买模型额度（充值/订阅）→ DSH 内注入我们的 key → 按 Token 用量计量扣费；运营方赚取模型差价并绑定用户。

**大图景关联**：Manus 式叙事中，模型层是**成本与毛利核心**（08/09 §8）—— 10 就是把这层变现的产品化。

## 3. 需求拆解

### 3.1 用户提出的
卖"带 Token 的 host"（09b 原意）→ 拆出后 = **卖 Token 额度本身**（用户可选：自带 key / 用平台额度）。

### 3.2 补充思考（"what else"）

**① 售卖形态（D1）**
- **余额钱包（推荐 MVP）**：充值 → 按 Token 用量扣费 → 余额不足提醒/停机；简单、透明；
- 订阅包（后置）：按月固定额度（如 ¥xx/月含 N 万 Token），超量按单价；
- 建议：MVP = 余额钱包。

**② 计量方式（D2）—— 10 的技术核心，需先查证**
- 方案 A：**DSH 自身用量**（日志/API 暴露 Token 统计）—— 最省事，但需查证 DSH 是否提供；
- 方案 B：**代理网关计量**（用户 key 指向我们的代理 → 转发 DeepSeek 并计量/限流）—— 精确可控，但引入代理层（可用/延迟/成本）；
- 方案 C：**DeepSeek 子 key/用量查询 API**（若开放平台支持签发子 key 或用量查询）—— 需查证；
- 建议：先查证 DSH 用量能力 + DeepSeek 开放平台能力，再定。

**③ 成本与毛利（D3）**
- 成本 = 模型 API 真实消耗（DeepSeek 官方价）；售价 = 成本 × 毛利系数（可配）；
- **成本敞口**：用户大 Token 用量 → 余额/用量上限/限流护栏前置（复用 08 配额 + 余额检查）。

**④ 合规（D4）—— 与 B11 同类的咨询项**
- **模型 API 转售条款**：DeepSeek 开放平台是否允许代理/转售？若不允许 → 换有转售授权的**算力合作方**，或调整模式（"代充值/代管 key"名义，边界需合规确认）；
- 与 09 的 B11（云资源转售）是不同性质：B11 管云资源，本项管模型 API 转售 —— 需分别咨询。

**⑤ 与 08/09 的关系（D5）**
- 前置依赖 08（支付/订单/账号）；
- 09a 可先行（用户自带 key），10 作为"免自带 key"增值与 09 并行/先后；**横切**：自有 host 用户同样可买额度。

**⑥ 用户体验**
- 云端 host：创建时选"用我的 key / 用平台额度"；
- 自有 host：portal 充值 → DSH 里填我们签发的 key（或一键注入）。
