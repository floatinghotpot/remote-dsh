# dsh 0.1.7-rc.1 兼容核验（remote-dsh 网关链路）

> **日期**: 2026-09-24
> **对象**: `@deepseek-ai/dsh@0.1.7-rc.1`（全局安装于 `/usr/local/lib/node_modules/@deepseek-ai/dsh`）与 remote-dsh
> **结论**: **网关链路兼容，无需功能改动**；`DSH_COMPAT_MAX` 已扩到 `0.1.7-rc.1`（见 §6）
> **关联**: [20260911-dsh-0.1.5-rc.2-plugin-compat](20260911-dsh-0.1.5-rc.2-plugin-compat.md)（同一份 G1–G7 清单的上一次核验）

---

## 1. 背景

dsh4vscode 为 0.1.7-rc.1 做了一次适配（`c1403dd fix: adapt to dsh 0.1.7-rc.1 base-relative plugin URLs`）：0.1.7 把插件引用改成 `<base>` 相对形式，扩展的 webview 因此报
`Failed to load plugins — client-modules: HTML did not preload …/client.js`。

remote-dsh 与扩展共用同一批 DSH 前端产物，因此需要核验：**这批 dist 形态变化是否同样破坏 remote-dsh 的网关链路**。

## 2. 上游变更（0.1.7-rc.1 实测）

| 项 | 0.1.5-rc.2 | **0.1.7-rc.1** | 出处 |
|---|---|---|---|
| `<base>` | 无（或 `/`） | **服务端在 `<head>` 后注入 `<base href="./">`** | `dsh-host-frontend-static/lib/index.js:85` |
| 插件 preload（`<link rel=preload>` / 引导 `<script src>`） | `/plugins/??…`（绝对） | **`plugins/??…`（相对）** | boot 注入行 `src: batch.url` |
| boot `entries[].url` / `batches[].url` | `/plugins/…`（绝对） | **`plugins/…`（相对）** | `comboReference()` / `buildBatch()` 用 `.slice(1)` 去掉前导 `/` |
| favicon | `favicon.svg` | `favicon.svg` + **`favicon-dark.svg`** | `dsh-web-frontend/dist/index.html` |
| application 批次 | 1 | **2** | — |
| 认证 / RPC | — | **未变**（就绪行、token、cookie、`/api` 信封格式一致，未观察到变化） | 见 §4 |

**关键点**：`dsh-client-modules` 内部仍以绝对 `/plugins` 为路由前缀（`PLUGIN_ROUTE = "/plugins"`），只在**写进文档的引用**上改成相对。

## 3. 为什么 dsh4vscode 受影响、remote-dsh 不受

- **dsh4vscode**：把 HTML 放进 `vscode-webview://<uuid>` 的 webview，相对 `plugins/…` 会按 **webview 自身的源**解析 → 404 → 引导脚本不加载 ⇒ 必须重写为服务器地址。
- **remote-dsh**：网关是**同源透明代理**。浏览器直接从 gateway/hub 的源（如 `https://rdsh.cn/`）加载页面，`plugins/…`（配 `<base href="./">` → 基址 `/`）由**浏览器**解析成绝对路径 `/plugins/…` 再发出；hub 侧 `packages/hub/src/server.ts:264` 是"有 host cookie 即全部路径转发"。相对引用对 remote-dsh **是 no-op**。
- 补充：`<base href="./">` 在 `<head>` 后注入，与 hub 的返回条注入点（`</head>` 前）不冲突。

## 4. 网关链路逐项核验（**真机实测**，真实 `dsh@0.1.7-rc.1`）

方法：仓库本地构建 `node packages/cli/dist/bin.js host serve --config <隔离配置>`（`mode=lan`、`auth.mode=none`、固定端口 45123、`dshPath=/usr/local/bin/dsh`、`DSH_HOME` 隔离），直接 spawn 全局 0.1.7-rc.1。

| # | 依赖点 | 实测证据 | 结果 |
|---|---|---|---|
| G1 | spawn 契约 `dsh web --port 0 --no-open` | 网关日志 `rdsh serve: dsh web on 127.0.0.1:51969`（OS 分配端口，无超时） | ✅ |
| G2 | ready 行解析 + launch token | `URL_LINE_RE` 命中 0.1.7 的 `dsh web: http://127.0.0.1:<port>/?token=…`（就绪行 `dsh web on 127.0.0.1:51969` 即解析成功）；且启动**无**"会话 cookie 换发失败"警告 | ✅ |
| G3 | 会话 cookie 换发（0.1.2+ 认证） | 由 G4 反证：`/api` 返回真实业务数据（非 401） | ✅ |

**版本警告实测**：扩窗前启动会打印
`⚠ 检测到 dsh 0.1.7-rc.1：该版本超出 remote-dsh 已实测范围（≤0.1.5-rc.2）…`，
同时**照常 spawn、照常服务**——佐证该警告仅 `console.warn`（`serve.ts:50` / `join.ts:1067`，注释即"warn（不硬拒）"），不阻断任何功能。

## 5. 未覆盖项

- **完整隧道人工 E2E（上次的 G9）**：本次未跑（未接生产 hub）。但 G4/G5/G6 已覆盖网关侧全部可能被 dist 形态影响的数据面环节；hub 对 `/api` + WS 是**版本无关的透明转发**（见 20260911 §2 第 4 行）。
- **非 macOS 平台**：本次在 macOS（Apple Silicon）实测；0.1.7 的变更是**前端 dist 形态**，与宿主 OS 无关。

## 6. 结论与改动

0.1.7-rc.1 的变更集中在**前端 dist 形态**，认证/RPC 未变；网关链路 G1–G7 全部通过 ⇒ **remote-dsh 无需功能改动**，只需把这批实测结果登记进版本窗口：

| 文件 | 改动 |
|---|---|
| `packages/gateway/src/spawn-dsh.ts` | `DSH_COMPAT_MAX`：`0.1.5-rc.2` → `0.1.7-rc.1`（并补核验注释） |
| `packages/gateway/test/spawn-dsh.test.ts` | "超窗"探针版本：`0.1.5-rc.3 / 0.1.5` → `0.1.7-rc.2 / 0.1.7`（旧探针在新窗口下会落回窗内、断言必失败——已实测复现） |

**下次 dsh 版本更新时重复 §4 的 G1–G7 清单即可。** 上游 `<base>` / 插件引用前缀策略仍在变，是历史故障率最高处（扩展侧 rc.8 / 0.1.1-rc.2 / 0.1.2-rc.1 / 0.1.7-rc.1 均在此），故每次 dsh 升级应首先核对 `GET /` 的 `<head>`。
