# DSH 0.1.2-rc.1 兼容性复核（remote-dsh）——浏览器会话认证是硬破坏，09-03 核验结论失效

> **日期**: 2026-09-07
> **对象**: `@deepseek-ai/dsh@0.1.2-rc.1` 与 remote-dsh（gateway / dsh-web-remote 插件 / hub）
> **关联**: 推翻 `doc/review/20260903-dsh-0.1.2-rc.1-compat.md` 的「兼容 ✅」结论
> **触发背景**: dsh4vscode 于 09-07 实测 0.1.2-rc.1（同款大版本）暴露三层破坏；本复核按同样方法重查 remote-dsh
> **结论**: **不兼容 ❌（P0 数据面阻断）**——remote-dsh 转发到 `dsh web` 的所有请求（index 文档 / `/api` RPC / WS upgrade）因缺失 authority 绑定 Cookie 一律 401，三种访问模式全部不可用

---

## 1. 背景

09-03 核验（下文称"旧核验"）只对 **3 个静态硬点**做了实包检查（spawn 契约 / 端口打印格式 / `patchLoopbackJs` 补丁目标），并依官方 release notes 断言"0.1.2 变更与仓库无交集"。该断言对**运行期行为**无效：0.1.2-rc.1 引入的"浏览器会话 Cookie 认证"是 09-03 完全未覆盖的破坏面，静态检查 + release notes 均无法暴露，须以实际启动 + 请求探测为准。

旧核验中仍成立的 3 点（本复核逐点重验）：

| 旧核验点 | 0.1.2-rc.1 现状 | 判定 |
|---|---|---|
| 1. `dsh web --port 0 --no-open` spawn | 保留（本机实测可启动） | ✅ 仍成立 |
| 2. 就绪行 `dsh web: http://127.0.0.1:<port>` | 行尾新增 `?token=<launchToken>`；`spawn-dsh.ts` 的 `URL_LINE_RE` 不锚定行尾 → 端口仍能解析，**但 token 被丢弃** | ✅ 解析成立 ⚠️ token 未用 |
| 3. patch 目标 `isLoopbackHostname(pageLocation.hostname)` | 0.1.2 `dsh-client-connection/lib/client.js` L4755 仍在 | ✅ 仍成立 |

## 2. 根因事实（dsh 0.1.2-rc.1 源码 + 本机实测）

### 2.1 认证模型（`dsh-client-connection/lib/index.js`）

- **Cookie 签发唯一入口**：`GET /?token=<launchToken>` → 303 + `Set-Cookie`；cookie 名 `dsh-auth-<base64url(sha256(authority))>`，payload 内嵌 `authority`，`HttpOnly; SameSite=Strict`，30 天；`authority` = 请求 `Host` 头的规范化形态（L229-258、L363-402）。
- **判定函数**：`requestRejection(request)` = Host/Origin 围栏（403） **且** `browserAuth.isAuthenticated`（**401**，无 cookie 即失败）（L530-533、L408-418）。
- **挂载点**：
  - `/api` 前缀路由（`apply` L705-714）：每个 `/api/*` 请求先过 `requestRejection`；
  - 各 RPC channel 注册路由（`register` L579-587）：同样先过 `requestRejection`；
  - `/` index 文档：`authorizeIndex`（`dsh-host-frontend-static/lib/index.js` L60/L95）——无 token 且无 cookie → 401；**非 index 静态资源公开**（L63-66）；
  - WS upgrade `/api/remote.mux`（`dsh-api-gateway/lib/index.js` L461-468）：upgrade 前同样 `requestRejection`。

### 2.2 本机实测（真实 `dsh@0.1.2-rc.1`，隔离 `DSH_HOME`，2026-09-07）

启动：`dsh web --port 0 --no-open` → 就绪行 `dsh web: http://127.0.0.1:57594/?token=lrXunNAqgiQUpmmE69CHadFIIut3Z2tUa0PE4TWa3cs`

模拟 rdsh 网关转发（Node 无 cookie 请求，Host 已为 loopback——即 `proxy.ts` / `join.ts` 的真实行为）：

| 探测 | 结果 |
|---|---|
| `GET /`（无 cookie，网关转发浏览器首请求） | **401** `dsh web authentication required` |
| `POST /api/workspace.list`（无 cookie） | **401** |
| WS upgrade `/api/remote.mux`（无 cookie，`ws` 客户端） | **401** |
| `GET /?token=` 换发 | 303 + `Set-Cookie: dsh-auth-<sha256(127.0.0.1:57594)>=v1…` |
| 换发后带 cookie `GET /` | **200** text/html |
| 带 cookie `POST /api/workspace.list` | 404（点号端点已废除——Typert 化佐证） |

> 与 dsh4vscode `doc/fix/20260907-dsh-0.1.2-rc1-auth/record.md` 实测结论一致：无 Cookie 的 `/`、`/api`、WS upgrade 全部 401。

## 3. 受影响组件矩阵

| 组件 | 与 dsh web 的接触方式 | 0.1.2-rc.1 | 说明 |
|---|---|---|---|
| **rdsh-gateway**（`packages/gateway`） | spawn `dsh web` + 转发到 `127.0.0.1:<port>`：`serve.ts`（LAN/云，经 `server.ts` `forwardHttp`/`createUpgradeProxy`）、`join.ts`（CLI 隧道 L402/L482） | 🔴 全挂 | 无 cookie → index/`/api`/WS 全 401 |
| **dsh-web-remote**（`packages/web-remote` v0.4.0） | 不 spawn，运行于 dsh web 进程内；隧道流量回环转发到自身 `ctx.webServer.port`（`src/index.ts` L159） | 🔴 全挂 | 同一转发内核，无 cookie → 401 |
| rdsh-hub（`packages/hub`） | 纯中继（auth/路由/隧道字节流），不 spawn 不转发到 dsh web | 🟢 无影响 | 对 dsh 版本无耦合 |
| rdsh-tunnel（`packages/tunnel`） | 线协议，与 dsh 无关 | 🟢 无影响 | — |
| rdsh-portal（`packages/portal`） | 调 hub API | 🟢 无影响 | — |
| rdsh-cli（`packages/cli`） | 编排层；spawn/转发经由 gateway `join()`/`serve()` | 🟢 随 gateway 修复 | `findDsh` 仅路径探测 |
| hub gate cookie 白名单 | 只认 `rdsh_gate`；`dsh-auth-*` 由宿主侧注入、不回传 hub | 🟢 语义干净 | — |

**破坏面本质**：两个受影响组件共享同一转发内核（`join.ts` 的 `openStream`/`openWsStream` + `proxy.ts` 的 `rewriteHeadersForDsh`/`forwardHttp`/`createUpgradeProxy`）——修复集中于此即可一次覆盖。

## 4. 修复方向（与 dsh4vscode 同构；未实施，仅供规划）

核心 = cookie 由 **rdsh 宿主侧（gateway / 插件）持有并注入**所有出站转发请求，而非暴露给远端浏览器：

1. **拿 token**：
   - CLI serve/join（进程外）：`spawn-dsh.ts` 就绪行正则扩展捕获 `?token=`（现被丢弃）；
   - dsh-web-remote 插件（进程内）：无 spawn 就绪行可解析；0.1.2 `HostConnectionService` 暴露 `authenticatedUrl()` 可进程内取带 token URL（需核对 0.1.1 老线是否缺失该方法，做版本分支）。
2. **换发**：就绪后/连接前，`node:http` 对 `GET /?token=` 做一次换发（`redirect:"manual"` 读 `Set-Cookie`，fetch 拿不到 opaque-redirect 的 cookie），持有 cookie；失败降级并记日志。
3. **注入**：`proxy.ts` `forwardHttp` + WS 升级代理、`join.ts` 隧道→本地转发，全部出站请求附加 `cookie` 头。cookie 的 authority 绑定由 Host 头决定，而 rdsh 恒将 Host 重写为 `127.0.0.1:<port>` → 一次换发对后续全部请求一致有效；dsh 崩溃重启后需重新解析就绪行并换发（secret 持久化于 credentials，launch token 为 per-process）。
4. **安全边界**：不把带 token URL 暴露给远端浏览器/hub 路径——宿主代持反而增强安全。

**适配范围文件（预估）**：`packages/gateway/src/spawn-dsh.ts`、`proxy.ts`、`join.ts`（+`serve.ts` 接线）、`packages/web-remote/src/index.ts`（token 入口）+ 单测。

## 4.5 破坏面 D：0.1.2 index gzip 破坏 hub HTML 注入（实测发现，2026-09-07 已修复）

认证适配实现后真机联调（真实 hub rdsh.cn）发现的**第二个破坏面**：

- **根因（实测）**：dsh 0.1.2 对 HTML 文档响应默认 `content-encoding: gzip` + `transfer-encoding: chunked`（0.1.1 无压缩）。hub `relay.ts` 的 `canInject` 要求 `content-encoding === undefined && transfer-encoding === undefined` → 跳过注入。
- **影响**：`BACK_BAR_HTML`（返回条）与 `E2EE_SHIM_HTML`（E2EE 数据面 shim）**双双不注入**——返回按钮消失，且 E2EE 静默降级为 plain（UI 正常但 hub 可读明文流量，README E2EE 承诺被破坏）。
- **修复**：`gateway/proxy.ts` `rewriteHeadersForDsh` 对**文档导航请求**（`Accept` 含 `text/html`）剥离 `accept-encoding` → dsh 返回明文 HTML（无 content-encoding）；`transfer-encoding` 由 `join.ts` `normalizeRespHeaders` 已滤。静态 JS/CSS 仍 gzip（压缩交给 hub TLS + E2EE 层）。一处覆盖 serve/join/插件三条路径（同时修好 serve 模式的 secure-context polyfill 注入）。
- **验证**：剥离后 dsh 响应无 `content-encoding`、body 含 `</head>`；单测 `rewriteHeadersForDsh：文档请求剥离 accept-encoding`；待真机回归（重启 join 后浏览器确认返回条 + E2EE shim 恢复）。

- 升级 dsh 后回归探测：`curl /` 核对 401 与否 + `<head>` 引用形态 + boot `batches`（同 dsh4vscode 建议）。
