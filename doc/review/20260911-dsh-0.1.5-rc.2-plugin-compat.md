# dsh 0.1.5-rc.2 兼容核验（dsh-web-remote / remote-dsh）

> **日期**: 2026-09-11
> **对象**: `@deepseek-ai/dsh@0.1.5-rc.2`（npm `next` 通道）与 remote-dsh
> **结论**: **插件链路与网关链路均已真机实测通过**；`DSH_COMPAT_MAX` 已扩到 `0.1.5-rc.2`（见 §4/§5）
> **关联**: [fix/20260911-dsh-0.1.5-plugin-rpc](../fix/20260911-dsh-0.1.5-plugin-rpc/discussion.md)、[20260907-dsh-0.1.2-rc.1-auth-gate-compat](20260907-dsh-0.1.2-rc.1-auth-gate-compat.md)

## 1. 背景

dsh 从 `0.1.2-rc.1` 升级到 `0.1.5-rc.2` 后，装有 `dsh-web-remote@0.5.0` 时 `dsh web` 无法启动（插件树加载失败）。本次核验：**是 remote-dsh 需要适配，还是上游回归**，以及适配后的兼容边界；并覆盖**网关链路**（`rdsh host serve` spawn dsh 并与其通信）。

## 2. 核验范围

| # | 链路 | 本次核验方式 |
|---|---|---|
| 1 | `dsh-web-remote` 插件（cordis 宿主内加载 + 浏览器 RPC 通道 + 浏览器半面板） | **运行时实测**（0.1.5-rc.2 与 0.1.2-rc.1 双版本；浏览器半在真实 profile 实测见 §5） |
| 2 | 网关 `rdsh host serve`（spawn `dsh web`、ready 行 token、会话 cookie 换发、`/api` 转发、HTML 注入、WS 桥接） | **运行时实测**（§6，真实 `dsh@0.1.5-rc.2`） |
| 3 | join 路径（隧道）的 dsh 侧环节（spawn/cookie + `patchLoopbackJs`） | **运行时实测**（G1–G3）+ **补丁命中实测**（G7）+ **完整 hub 端到端人工实测**（G9，§6） |
| 4 | hub 对 `/api` + WS 的透明转发 | dsh 版本无关（不解析流量），不在本次范围 |

## 3. 插件链路：根因与结论

**是上游回归，不是 remote-dsh 误用**。`dsh-client-connection@0.1.5-rc.2` 的 `register()`（`lib/index.js:618`）在 reader 的 shadow ctx 上访问 `owner.webServer`，第三方插件行无法解析该服务 → apply 抛错 → 整棵插件树加载失败。

- 已用最小探针插件复现并排除：cordis 4.0.1 vs 4.0.2 **逐字节相同**；我们 `dist` 确有 `export const inject = ["connection","webServer"]`；bundle patch 行级 `inject` 补写无效；`ctx.webServer` 直接访问/`ctx.effect`/`ctx.inject` 包装全部无效，唯 `rpc.handle` 失败。
- 上游同症状公开讨论：[deepseek-harness #5926](https://github.com/deepseek-ai/deepseek-harness/discussions/5926)（无 ETA）。
- 生态实证：同类第三方插件 [dsh-mobile-gateway](https://github.com/agent-mobile/dsh-mobile-gateway) 在 0.1.5 上用 `ctx.webServer.register({kind:"prefix",…})` 自挂路由，不用 `rpc.handle`。

| `connection.requestRejection(request)` | `dsh-client-connection/lib/index.js:530` | 第 553 行 | ✅ 一致 |
| `connection.createSharedFetchHandler(channel)` | 第 547 行 | 第 570 行 | ✅ 一致 |
| 浏览器 `rpc.call` 线协议（`client-request`/`server-response` + rpcId 回显） | `client.js` 同构 | `client.js` 同构 | ✅ 一致 |
| 官方 `/api` 桥状态语义（404 方法/端点、415 内容类型、413 超限、400 非 JSON、500 handler 抛错；envelope 非法与 `method`/path 不一致 → 200 + `gateway/bad-request`） | 同构（逐条比对 `rpcFetchHandler`） | 同构 | ✅ 一致 |
| `rpc.handle` | 可用（我们原方案） | **不可用（回归）** | ❌ 已弃用 |

⇒ 适配后**无需版本分支**，同一份代码覆盖两版。

## 6. 网关链路：**真机实测通过**（2026-09-11）

`rdsh host serve`（局域网网关，`mode=lan`，隔离配置 `--config /tmp/rdsh-gw/host.json`，`auth.mode=none`，端口 0）直接 spawn 全局 `dsh@0.1.5-rc.2`：

| # | 依赖点 | 实测证据 | 结果 |
|---|---|---|---|
| G1 | spawn 契约 `dsh web --port 0 --no-open` | 网关日志 `rdsh serve: dsh web on 127.0.0.1:54478`（OS 分配端口，无超时/报错） | ✅ |
| G2 | ready 行解析 + launch token | `URL_LINE_RE` 命中 0.1.5 的 `dsh web: http://127.0.0.1:<port>/?token=…`；网关启动**无 cookie 换发失败警告** | ✅ |
| G3 | 会话 cookie 换发（0.1.2+ 认证层） | 后续 `/api` 调用返回真实业务数据（非 401）⇒ `dsh-auth-*` cookie 已成功换发并注入 | ✅ |
| G4 | Host/Origin 重写 + `/api` 转发 | `POST /api/settings/describe` → `200` + `{"result":{"ok":true,"value":{"writable":true,…}}}`；`POST /api/session/list` → 200 + DSH 自身 `gateway/arguments-invalid` 业务错误（证明请求已进入 DSH 分发器） | ✅ |
| G5 | HTML 注入（非 secure context polyfill，含 0.1.2 起的 gzip 剥离） | `GET /`（`accept: text/html`）→ `200 text/html`，注入脚本命中（`crypto.randomUUID` polyfill 1 处），`<title>` 完好 | ✅ |
| G6 | WebSocket 升级桥接 | `ws://127.0.0.1:<gw>/api/remote.mux` → **OPEN（101 握手 + 上游桥接）** | ✅ |
| G7 | join 路径的前端补丁 `patchLoopbackJs` | 对**真实** 0.1.5-rc.2 客户端 bundle 调用：目标串命中 1 处、patch 后残留 0；0.1.2-rc.1 同样命中 | ✅ |

**WS 路径说明（非本次破坏，且与我们无关）**：`events.mux` / `events.host` 在 **0.1.2** 就已被单一 `/api/remote.mux`（`dsh-api-gateway` 的 `REMOTE_STREAM_MUX_PATH`）取代（0.1.2-rc.1 与 0.1.5-rc.2 均只有 `remote.mux`）。网关/hub 对 WS 一律按 `req.url` 原样透传，**不硬编码路径**，因此路径更名不影响转发。仓库内仅**注释与测试用例**仍用旧名（`packages/hub/src/relay.ts:176`、`server.ts:168` 注释；`packages/gateway/test/*.test.ts` 的假上游路径），无功能依赖。

**结论**：网关链路在 0.1.5-rc.2 上**未发现兼容性破坏** ⇒ `DSH_COMPAT_MAX` 已扩到 `0.1.5-rc.2`（`packages/gateway/src/spawn-dsh.ts`），并补 `dshVersionWarning` 窗口边界单测；扩展后重跑上述 G2/G4/G5/G6 全部通过、版本警告消失。

**G9｜完整隧道端到端（人工实测 ✅）**：2026-09-11 在本机以 `rdsh host serve`（join 模式，hub `https://rdsh.cn`，主机 `iMacPro`）连接生产 hub，日志 `tunnel established (heartbeat 30s)`、无版本警告、无 cookie 换发失败警告；**用户从远端设备经 hub 实际访问本机 DSH 成功**（`https://rdsh.cn/h/<host-id>/`；hostId 属内部标识，不入公开仓）。这覆盖了此前唯一未验证的环节：远端浏览器 → hub → host → dsh（含 E2EE 数据面与前端补丁的真实生效），且未发现 0.1.5 相关破坏。测试后已停止隧道，`join.lock` 随优雅退出释放。

## 7. 发布记录（2026-09-11）

修复发布为三个包，均已上线并按 registry 产物核对（`npm view` + tarball 内容校验）：

| 包 | 版本 | 核对要点 |
|---|---|---|
| `rdsh-gateway` | 0.8.2 | `dist/spawn-dsh.js` 含 `DSH_COMPAT_MAX = "0.1.5-rc.2"` |
| `dsh-web-remote` | 0.5.1 | 含 `dist/rpc-route.js`；`index.js` 引用 `handleRpcRoute`；依赖 `rdsh-gateway 0.8.2` |
| `remote-dsh`（CLI） | 0.10.2 | 依赖 `rdsh-gateway 0.8.2` + `rdsh-hub 0.7.0` |

> **发布过程记录（踩坑）**：`dsh-web-remote@0.5.1` 首次发布走了 npm 12 的 **staged publish** —— 命令报 `✅ Published`，但版本进入「staged（待批准）」状态，registry 上不可见（`latest` 仍是 0.5.0、`npm view <pkg>@0.5.1` 404），随后重发会报 `409 Cannot publish over previously staged version "0.5.1"`。正确处理是先用 `npm stage list <pkg>` / `npm stage approve <stage-id>`（npm 12 的 `npm stage` 子命令）；**不要为此改版本号**。本次 staged 版本随后被批准入网，`latest` 已指向 0.5.1。
>
> 另：pnpm ≥ 12 的 `minimumReleaseAge` 会让消费者在发布后 24h 内装到旧版 —— 用户侧安装请钉版本：`dsh plugin --profile web add dsh-web-remote@0.5.1`。

## 8. 建议

1. 升级 dsh 到 `0.1.5-rc.2` 的用户：安装 `dsh-web-remote@0.5.1`（含本次修复）后重试；0.5.0 在 0.1.5-rc.2 上必然导致 `dsh web` 起不来，可临时移除插件或回退 dsh。
2. `DSH_COMPAT_MAX` 已扩到 `0.1.5-rc.2`（2026-09-11 实测）；下次 dsh 版本更新时重复 §5 的 G1–G7 清单即可。
3. 关注上游 #5926 的修复；若上游恢复 `rpc.handle`，我们**无需回退**——原生路由方案在两版均可用且不依赖该 helper。
